## Что проверить

### Определение проблемы (Критично)
- План чётко описывает, какая проблема решается
- Описание проблемы конкретное, не размытое
- Критерии успеха указаны явно или неявно

### Корректность решения (Критично)
- Предложенное решение действительно решает заявленную проблему
- Нет пропущенных шагов, которые оставили бы проблему нерешённой
- Краевые случаи учтены

### Оценка объёма (Важно)
- Объём адекватный — не слишком широкий, не слишком узкий
- Нет расползания объёма (посторонние фичи в комплекте)
- Зависимости между задачами логичны

### Выявление переусложнения (Критично)
Паттерны для обнаружения:
- Необходимые абстракции
- Преждевременное обобщение
- Злоупотребление паттернами (использование паттернов проектирования, где достаточно простого кода)
- Фичи "на всякий случай" (нарушения YAGNI)
- Избыточная многослойность
- Сложность там, где достаточно простого решения

### Требования к тестированию (Критично)
- Каждая задача включает написание тестов как отдельные пункты чеклиста
- Указаны тесты для успешных И ошибочных сценариев
- Присутствует шаг "Запустить тесты" в каждой задаче
- Указано расположение тестов (путь к файлу тестов)

### Обнаружение заглушек (Критично)
Отметь любые из этих паттернов — они являются ошибками плана:
- "TBD", "TODO", "implement later", "fill in details"
- "Add appropriate error handling" / "add validation" / "handle edge cases"
- "Write tests for the above" (без фактического кода тестов)
- "Similar to Task N" (без повторения кода)
- Шаги, описывающие что сделать, без показа как

### Гранулярность задач (Важно)
- Задачи представляют одну логическую единицу (не несколько фич в комплекте)
- Конкретные названия, не общие вроде "[Core Logic]"
- Примерно 5 чекбоксов на задачу (больше — допустимо, если атомарно)
- Чёткая прогрессия от задачи к задаче

### Согласованность типов (Важно)
- Имена функций/методов согласованы между задачами
- Имена параметров и типы совпадают между определениями и использованием
- Нет ссылок на типы или функции, не определённые ни в одной задаче

### Сопровождаемость (Важно)
- Решение даст читаемый, сопровождаемый код
- Нет "хитрых" решений там, где достаточно понятных
- Адекватная декомпозиция

## Ключевые принципы

1. **Отмечай только те проблемы, которые вызовут реальные трудности при реализации.**
2. **Одобряй, если нет серьёзных пробелов** — пропущенные требования, противоречивые шаги, содержимое-заглушка или задачи настолько размытые, что их невозможно выполнить.
3. Мелкие формулировки, стилистические предпочтения и "желательные" предложения — не являются проблемами.
4. Простое лучше хитрого. Предпочитай прямолинейные решения.
5. Если не уверен, является ли что-то переусложнением — отметь это как вопрос, а не как проблему.
