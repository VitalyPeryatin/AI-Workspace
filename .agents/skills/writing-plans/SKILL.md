# Написание планов

Создание структурированных планов реализации через интерактивный сбор контекста.

**Объявить в начале:** "Я использую скилл writing-plans для создания плана реализации."

**Сохранять планы в:** `docs/plans/YYYY-MM-DD-<feature-name>.md`

## Директория скилла

Когда этот скилл загружен, базовый путь директории указан в выводе загрузки. Используй этот путь как `SKILL_DIR` для запуска скриптов:

- Скрипты: `SKILL_DIR/scripts/<name>.sh`

## Шаг 0: Разбор намерений и сбор контекста

Перед тем как задавать вопросы, пойми, над чем работает пользователь.

1. **Разбери запрос пользователя** для определения намерения:
   - "add feature Z" / "implement W" → разработка фичи
   - "fix bug" / "debug issue" → план исправления бага
   - "refactor X" / "improve Y" → план рефакторинга
   - "migrate to Z" / "upgrade W" → план миграции
   - общий запрос → исследовать текущую работу

2. **Собери релевантный контекст** — используй инструменты Read, Glob, Grep напрямую. Уложись в 30 секунд:

   **Для разработки фичи:**
   - Glob для файлов, соответствующих области фичи (например, `**/*auth*`, `**/*cache*`)
   - Прочитай 1-3 наиболее релевантных файла для понимания существующих паттернов
   - Проверь структуру проекта быстрым листингом ключевых директорий

   **Для исправления бага:**
   - Grep по сообщениям об ошибках или названиям функций из запроса
   - Прочитай конкретные задействованные файлы
   - Проверь `git log --oneline -5` на предмет недавних изменений

   **Для рефакторинга/миграции:**
   - Glob для файлов, соответствующих области рефакторинга
   - Прочитай 2-3 ключевых файла для понимания текущей структуры
   - Grep по импортам/ссылкам для выявления зависимостей

   **Для общих/нечётких запросов:**
   - Проверь `git status` и `git log --oneline -5`
   - Прочитай README.md или AGENTS.md для обзора проекта
   - Выведи структуру директорий верхнего уровня

   **КРИТИЧЕСКИ ВАЖНО:** НЕ запускай Task-субагент для исследования и не читай более 5 файлов на этом шаге. Только быстрое сканирование.

3. **Синтезируй результаты** в краткое резюме контекста (3-5 пунктов):
   - Что за проект и основной язык/фреймворк
   - Какие файлы/области релевантны запросу
   - Ключевые паттерны или соглашения, обнаруженные в проекте

## Шаг 1: Представь контекст и задай сфокусированные вопросы

Покажи обнаруженный контекст, затем задавай вопросы **по одному** с помощью инструмента `question`:

"Я обнаружил следующий контекст: [резюме контекста]"

**Задавай вопросы по одному:**

1. **Цель плана** — "Какова основная цель?" Предложи варианты на основе обнаруженного намерения.
2. **Объём** — "Какие компоненты/файлы задействованы?" Предложи варианты с обнаруженными файлами/областями.
3. **Ограничения** — "Есть ли специфические требования или ограничения?" Может быть открытым вопросом, если ограничения сильно различаются.
4. **Подход к тестированию** — "Предпочитаешь TDD или обычный подход?" Варианты: "TDD (сначала тесты)" и "Обычный (сначала код, потом тесты)".
5. **Название плана** — "Краткое описательное название?" Предложи имя на основе намерения.

Жди ответа на каждый вопрос перед тем, как задать следующий.

После ответов на все вопросы синтезируй ответы в контекст плана.

## Шаг 1.5: Исследование подходов

Когда проблема понята, предложи подходы к реализации:

1. **Предложи 2-3 разных подхода** с оценкой компромиссов для каждого
2. **Начни с рекомендуемого варианта** и обоснуй выбор
3. **Представляй в формате диалога** — пока не формальный документ

Пример формата:
```
Вижу три подхода:

**Вариант А: [название]** (рекомендуемый)
- как работает: ...
- плюсы: ...
- минусы: ...

**Вариант Б: [название]**
- как работает: ...
- плюсы: ...
- минусы: ...

Какое направление тебе ближе?
```

Используй инструмент `question`, чтобы пользователь мог выбрать предпочтительный подход.

**Пропусти этот шаг**, если:
- Подход к реализации очевиден (единственный ясный путь)
- Пользователь явно указал, как он хочет это сделать
- Это исправление бага с понятным решением

## Шаг 2: Создай файл плана

Проверь `docs/plans/` на наличие существующих файлов, затем создай `docs/plans/YYYY-MM-DD-<task-name>.md`.

### Структура файлов до задач

Перед определением задач наметь, какие файлы будут созданы или изменены и за что каждый отвечает. Именно здесь фиксируются решения о декомпозиции.

- Проектируй модули с чёткими границами и хорошо определёнными интерфейсами. Каждый файл должен иметь одну ясную зону ответственности.
- Предпочитай меньшие, сфокусированные файлы вместо больших, делающих слишком много.
- Файлы, которые меняются вместе, должны находиться вместе. Разделяй по ответственности, а не по техническим слоям.
- В существующих кодовых базах следуй устоявшимся паттернам.

### Шаблон плана

````markdown
# [Название плана]

**Цель:** [Одно предложение, описывающее, что строится]

**Архитектура:** [2-3 предложения о подходе]

**Технологический стек:** [Ключевые технологии/библиотеки]

---

## Обзор
- Чёткое описание фичи/изменения, которое реализуется
- Какую проблему решает и ключевые преимущества
- Как интегрируется с существующей системой

## Контекст (из исследования)
- Задействованные файлы/компоненты: [список из шага 0]
- Найденные связанные паттерны: [обнаруженные паттерны]
- Выявленные зависимости: [зависимости]

## Подход к разработке
- **Подход к тестированию**: [TDD / Обычный — из предпочтения пользователя]
- Полностью завершай каждую задачу перед переходом к следующей
- Делай небольшие, сфокусированные изменения
- **КРИТИЧЕСКИ: каждая задача ДОЛЖНА включать новые/обновлённые тесты** для изменений кода в этой задаче
- **КРИТИЧЕСКИ: все тесты должны проходить перед началом следующей задачи**
- **КРИТИЧЕСКИ: обновляй этот файл плана при изменении объёма в процессе реализации**
- Запускай тесты после каждого изменения
- Поддерживай обратную совместимость

## Структура файлов
- Создать: `точный/путь/к/новому_файлу` — [зона ответственности]
- Изменить: `точный/путь/к/существующему` — [что меняется]
- Создать: `точный/путь/к/файлу_тестов` — [что тестирует]

## Отслеживание прогресса
- отмечай выполненные пункты `[x]` сразу после завершения
- добавляй вновь обнаруженные задачи с префиксом ➕
- документируй проблемы/блокеры с префиксом ⚠️
- обновляй план, если реализация отклоняется от изначального объёма
- держи план в синхроне с фактически выполненной работой

## Обзор решения
- высокоуровневый подход и выбранная архитектура
- ключевые проектные решения и их обоснование
- как это вписывается в существующую систему

## Технические детали
- структуры данных и изменения
- параметры и форматы
- поток обработки

## Что куда относится
- **Шаги реализации** (чекбоксы `[ ]`): задачи, выполнимые в рамках этой кодовой базы — изменения кода, тесты, обновление документации
- **После завершения** (без чекбоксов): элементы, требующие внешних действий — ручное тестирование, изменения в потребляющих проектах, конфигурация развёртывания, проверки сторонних сервисов

## Шаги реализации

### Задача 1: [конкретное название — цель этой задачи]

**Файлы:**
- Создать: `точный/путь/к/новому_файлу`
- Создать: `точный/путь/к/файлу_тестов`
- Изменить: `точный/путь/к/существующему`

- [ ] **Шаг 1: Напиши реализацию**

[блок кода с фактическим кодом реализации]

- [ ] **Шаг 2: Напиши тест**

[блок кода с фактическим кодом тестов]

- [ ] **Шаг 3: Запусти тест и убедись, что он проходит**

Запустить: `конкретная команда для запуска теста`
Ожидается: PASS

- [ ] **Шаг 4: Закоммить**

```bash
git add <файлы>
git commit -m "feat: <конкретное описание>"
```

### Задача N-1: Проверь критерии приёмки
- [ ] Убедись, что все требования из Обзора реализованы
- [ ] Убедись, что краевые случаи обработаны
- [ ] Запусти полный набор тестов: `<команда тестирования модуля>`

### Задача N: Обнови документацию
- [ ] Обнови README.md при необходимости
- [ ] Обнови AGENTS.md, если обнаружены новые паттерны
- [ ] Перенеси этот план в `docs/plans/completed/`

## После завершения
*Элементы, требующие ручного вмешательства или внешних систем — без чекбоксов, только для информации*

**Ручная проверка** (если применимо):
- Сценарии ручного тестирования UI/UX
- Нагрузочное тестирование производительности
- Соображения по безопасности

**Обновления внешних систем** (если применимо):
- потребляющие проекты, требующие обновления после изменения этой библиотеки
- изменения конфигурации в системах развёртывания
- проверки интеграций со сторонними сервисами
````

### Гранулярность задач

**Каждый шаг — это одно действие (2-5 минут):**
- "Написать падающий тест" — шаг
- "Запустить и убедиться, что он падает" — шаг
- "Реализовать минимальный код, чтобы тест прошёл" — шаг
- "Запустить тесты и убедиться, что они проходят" — шаг
- "Закоммить" — шаг

Каждая задача = ОДНА логическая единица (одна функция, один эндпоинт, один компонент).
Целевое значение ~5 чекбоксов на задачу (больше — допустимо, если логически атомарно).
Каждая задача ДОЛЖНА заканчиваться написанием/обновлением тестов перед переходом к следующей.

## Без заглушек

Каждый шаг должен содержать фактическое содержание, нужное инженеру. Следующее — **ошибки плана** — никогда их не пиши:

- "TBD", "TODO", "implement later", "fill in details"
- "Add appropriate error handling" / "add validation" / "handle edge cases"
- "Write tests for the above" (без фактического кода тестов)
- "Similar to Task N" (повтори код — инженер может читать задачи не по порядку)
- Шаги, описывающие что сделать, без показа как (для шагов с кодом требуются блоки кода)
- Ссылки на типы, функции или методы, не определённые ни в одной задаче

## Самопроверка

После написания полного плана прогони этот чеклист сам — не через субагент:

**1. Покрытие спецификации:** Просмотри каждую секцию/требование в спецификации. Можешь указать на задачу, которая его реализует? Перечисли пробелы.

**2. Поиск заглушек:** Поищи в своём плане тревожные сигналы — любые паттерны из секции "Без заглушек" выше. Исправь их.

**3. Согласованность типов:** Совпадают ли типы, сигнатуры методов и имена свойств, использованные в поздних задачах, с тем, что ты определил в ранних задачах? Функция `clearLayers()` в Задаче 3, но `clearFullLayers()` в Задаче 7 — это баг.

Если найдены проблемы — исправь их на месте. Если найдено требование спецификации без задачи — добавь задачу.

## Шаг 3: Следующие шаги

После создания файла плана сообщи: "Создан план: `docs/plans/YYYY-MM-DD-<task-name>.md`"

Затем используй инструмент `question`:

```
header: "Ревью плана"
question: "План создан. Что дальше?"
options:
  - label: "Агент ревью плана"
    description: "Запустить AI-агент ревью плана для автоматического анализа"
  - label: "Аннотация Plannotator"
    description: "Открыть интерактивный UI аннотации для ручного ревью"
  - label: "Готово"
    description: "Закоммитить план, без дальнейших действий"
```

### Агент ревью плана

Отправь один субагент plan-document-reviewer (см. plan-reviewer-prompt.md) с точно сформулированным контекстом ревью — никогда не передавай историю своей сессии. Это держит ревьюера сфокусированным на плане, а не на твоём мыслительном процессе.
После завершения ревью спроси пользователя снова с оставшимися опциями (без "Агент ревью плана").

### Аннотация Plannotator

Запусти `bash SKILL_DIR/scripts/plannotator-annotate.sh <ПУТЬ_К_ФАЙЛУ_ПЛАНА>` через bash (используй абсолютный путь к файлу плана). Это **блокирующий вызов** — он запускает сервер аннотаций Plannotator, открывает браузер и ждёт, пока пользователь нажмёт "Send Feedback" или "Approve". Вывод команды содержит обратную связь пользователя в виде структурированного текста.
Когда обратная связь получена:
1. прочитай каждую аннотацию — номер строки и комментарий описывают, что пользователь хочет изменить
2. внеси изменения в файл плана для учёта каждой аннотации
3. снова запусти `bash SKILL_DIR/scripts/plannotator-annotate.sh <ПУТЬ_К_ФАЙЛУ_ПЛАНА>` через bash
4. вывод содержит следующий раунд обратной связи
5. повторяй, пока вывод не укажет на одобрение без изменений

После завершения цикла аннотаций спроси пользователя снова с оставшимися опциями.

### Готово

Закоммить план с сообщением вида `docs: add <topic> implementation plan`, затем предложи выполнение:

```
header: "Выполнение"
question: "Как выполнить этот план?"
options:
  - label: "Скилл Exec"
    description: "Загрузить скилл execute-plan для полного выполнения плана с циклом задач и многоэтапным ревью кода"
  - label: "Инлайн-выполнение"
    description: "Выполнить задачи напрямую в этой сессии"
```

**Если выбран скилл Exec:** Вызови скилл `execute-plan` через инструмент skill.
**Если выбрано Инлайн-выполнение:** Выполни задачи плана напрямую в текущей сессии, завершая каждую задачу последовательно.

## Ключевые принципы

- **Один вопрос за раз** — не перегружай несколькими вопросами
- **Выбор из вариантов** — проще отвечать, чем формулировать открытый ответ, когда возможно
- **DRY, YAGNI безжалостно** — избегай ненужного дублирования и фич, минимизируй объём (но предпочитай дублирование преждевременной абстракции, когда это снижает связанность)
- **Начинай с рекомендации** — имей мнение, объясняй почему, но решение за пользователем
- **Исследуй альтернативы** — всегда предлагай 2-3 подхода перед тем как остановиться на одном (если не очевидно)
- **Всегда точные пути файлов** — никакой относительной двусмысленности
- **Полный код в каждом шаге** — если шаг меняет код, покажи код
- **Точные команды с ожидаемым выводом** — без угадывания
