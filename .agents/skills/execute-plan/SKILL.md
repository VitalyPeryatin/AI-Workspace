# execute-plan

Выполнение задач из файла плана последовательно, каждая — в изолированном субагенте.

## Аргументы

- `$ARGUMENTS` — путь к файлу плана (необязательно; если не указан, выбрать из `docs/plans/`)

## Директория скилла

Когда этот скилл загружен, базовый путь директории указан в выводе загрузки. Используй этот путь как `SKILL_DIR` для чтения файлов ссылок и запуска скриптов:

- Файлы промптов: `SKILL_DIR/references/prompts/<name>.md`
- Файлы агентов: `SKILL_DIR/references/agents/<name>.txt`
- Скрипты: `SKILL_DIR/scripts/<name>.sh`

## Подстановка плейсхолдеров

После чтения файла промпта замени ВСЕ плейсхолдеры на фактические значения перед передачей субагенту. Субагенты запускаются в чистом контексте без контекста скилла.

Всегда подставляй: `PLAN_FILE_PATH`, `PROGRESS_FILE_PATH`, `DEFAULT_BRANCH`, `WORK_DIR`, `SKILL_DIR` (разрешённый абсолютный путь), `AGENTS_DIR` (разрешённый в `SKILL_DIR/references/agents`), а также значения для конкретных фаз (`FINDINGS_LIST`, `REVIEW_PHASE`).

Когда `WORK_DIR` не пуст (режим worktree), разреши `PLAN_FILE_PATH` и `PROGRESS_FILE_PATH` в абсолютные пути внутри worktree (например, `WORK_DIR/docs/plans/plan-name.md`, `WORK_DIR/docs/progress/progress-name.txt`).

## Процесс

### Шаг 1. Определение файла плана

Если `$ARGUMENTS` содержит путь к файлу — используй его. Иначе выведи список `.md` файлов в `docs/plans/`, исключая `completed/`. Если найден ровно один план — используй его автоматически. Если несколько — попроси пользователя выбрать через инструмент `question`.

Прочитай файл плана. Посчитай общее количество секций Task (`### Task N:` или `### Iteration N:`), чтобы понимать объём.

Зафиксируй текущую ветку — это базовая ветка (DEFAULT_BRANCH), используемая позже для diff'ов при ревью:

```bash
git branch --show-current
```

### Шаг 2. Вопрос об изоляции через worktree

Спроси пользователя через инструмент `question`, запускать ли в изолированном git worktree или в текущей рабочей директории:

- **Worktree** — создаёт изолированную копию репозитория через скилл `using-git-worktrees`. Чистое отделение от основной рабочей директории. Лучше для долгих планов, когда нужно продолжать работу в основном репозитории.
- **Текущая директория** — работает прямо в текущем репозитории. Проще, но блокирует рабочую директорию на время выполнения.

Если пользователь выбрал "Worktree", вызови скилл `using-git-worktrees` через инструмент skill. Передай имя ветки (произведённое от имени файла плана — убери префикс даты, например `2026-05-13-feature.md` → `feature`). После завершения скилла зафиксируй абсолютный путь worktree как `WORK_DIR`. Разреши `PLAN_FILE_PATH` в `WORK_DIR` + оригинальный относительный путь (например, `WORK_DIR/docs/plans/plan-name.md`). Все последующие вызовы Bash tool orchestrator'а, затрагивающие репозиторий, ДОЛЖНЫ включать `workdir: WORK_DIR`. По завершении сообщи путь worktree и имя ветки для ревью и мержа пользователем.

Если пользователь выбрал "Текущая директория", установи `WORK_DIR` в пустую строку. Продолжай как обычно.

### Шаг 3. Создание списка задач

ВСЕГДА создавай задачи через `todowrite` перед началом любой работы. Создай одну задачу на каждую секцию Task в плане плюс фазы ревью:

Для каждой секции `### Task N:` в плане:
- Добавь задачу: `{"content": "Task N: <заголовок>", "status": "pending", "priority": "high"}`

Затем добавь задачи ревью:
- `{"content": "Фаза ревью 1: комплексная", "status": "pending", "priority": "medium"}`
- `{"content": "Фаза ревью 2: код-смеллы", "status": "pending", "priority": "medium"}`
- `{"content": "Фаза ревью 3: только критичное", "status": "pending", "priority": "medium"}`
- `{"content": "Фаза ревью 4: ручное ревью", "status": "pending", "priority": "medium"}`

Обновляй задачи по ходу: устанавливай `"status": "in_progress"` при старте, `"status": "completed"` при завершении.

### Шаг 4. Создание ветки

Если worktree был выбран на Шаге 2, пропусти этот шаг — скилл worktree уже создал ветку. Иначе:

Произведи имя ветки из файла плана, убрав префикс даты (например, `2026-05-13-feature-name.md` → `feature-name`). Создай новую ветку от текущей. Если ветка уже существует — просто переключись на неё.

Зафиксируй и используй имя ветки для последующих шагов.

### Шаг 5. Инициализация файла прогресса

Создай директорию прогресса при необходимости: `mkdir -p docs/progress` (используй `workdir: WORK_DIR`, когда `WORK_DIR` задан).

Инициализируй файл прогресса: `bash SKILL_DIR/scripts/init-progress.sh docs/progress/progress-<plan-name>.txt <plan-file-path> <branch-name>` (имя `<plan-name>` — от stem'а файла плана, например `fix-issues.md` → `progress-fix-issues`). Когда `WORK_DIR` задан, разреши `PROGRESS_FILE_PATH` в `WORK_DIR/docs/progress/progress-<plan-name>.txt`. Скрипт создаёт файл с заголовком. Сообщи пользователю полный путь к файлу прогресса.

ВАЖНО: Всегда используй `SKILL_DIR/scripts/append-progress.sh` для записи в файл прогресса после инициализации. Никогда не пиши напрямую.

### Шаг 6. Цикл задач

Повторяй, пока в любой секции Task остаются чекбоксы `[ ]`:

1. **Перечитай файл плана** (субагент модифицирует его каждую итерацию)
2. **Найди первую секцию Task** (`### Task N:` или `### Iteration N:`), в которой ещё есть чекбоксы `[ ]`
3. **Если не найдено** — все задачи завершены, переходи к шагу 7
4. **Объяви задачу пользователю** — перед запуском субагента выведи видимое резюме:
   - Номер и заголовок задачи (из заголовка `### Task N:`)
   - Список всех пунктов с чекбоксами `[ ]` в этой секции
5. **Запусти субагент** через инструмент Task с:
   - `subagent_type: "general"`
   - Промпт задачи из `SKILL_DIR/references/prompts/task.md`, со всеми подставленными плейсхолдерами (PLAN_FILE_PATH, PROGRESS_FILE_PATH, WORK_DIR, SKILL_DIR разрешён в абсолютный путь)
6. **После возврата субагента** перечитай файл плана и проверь, что чекбоксы этой задачи теперь `[x]`
   - Если да — задача выполнена, продолжай цикл
   - Если нет — **повтори** с новым субагентом для той же задачи до 3 раз. Если повторная попытка не удалась — остановись и сообщи пользователю о провале
7. **Сообщи пользователю**: "Задача N завершена"

КРИТИЧЕСКИ: НЕ останавливай цикл на основе текста возврата субагента. ЕДИНСТВЕННОЕ условие остановки: в любой секции Task не осталось чекбоксов `[ ]`. Всегда перечитывай файл плана для проверки.

КРИТИЧЕСКИ: Ты — ОРКЕСТРАТОР. Никогда не читай код, не отлаживай ошибки, не исследуй диагностику и не исправляй проблемы сам. Если субагент оставляет проблемы (ошибки компиляции, падения тестов, lint-проблемы) — повтори с новым субагентом, передай детали ошибки в промпте, чтобы он мог их исправить. Вся работа с кодом происходит внутри субагентов, а не в оркестраторе.

Максимум итераций для безопасности: 20. Если достигнут — остановись и сообщи пользователю.

### Шаг 7. Фаза ревью 1 — комплексная, затем критичная перепроверка

После завершения всех задач проведи комплексное ревью кода на итерации 1, затем сузь до только критичных перепроверок на последующих итерациях.

Сообщи пользователю: "--- Фаза ревью 1: комплексная ---"

Цикл до 5 раз. Отслеживай номер текущей итерации:

1. **Запусти агент ревью** — прочитай промпт ревью из `SKILL_DIR/references/prompts/review.md`. Запусти один вызов Task tool с `subagent_type: "general"` и промптом. Замени DEFAULT_BRANCH, PLAN_FILE_PATH, PROGRESS_FILE_PATH и AGENTS_DIR (разрешённый в абсолютный путь `SKILL_DIR/references/agents`).
   - **Итерация 1**: установи REVIEW_PHASE в `comprehensive`. Агент ревью запускает 4 агента параллельно (качество, реализация, тестирование, упрощение).
   - **Итерация 2 и далее**: установи REVIEW_PHASE в `critical`. Агент ревью запускает 2 агента (качество, реализация), сфокусированных только на критичных/мажорных проблемах. Перед этой итерацией сообщи пользователю: "--- Фаза ревью 1: критичная перепроверка (итерация N) ---"

2. **Собери находки** — передай ПОЛНЫЙ вывод агента ревью (не резюме) в fixer. НЕ резюмируй, не фильтруй и не отбрасывай ни одну находку. ВСЕ находки требуют действий. Сообщи пользователю краткий список находок. Запиши в файл прогресса:
   `bash SKILL_DIR/scripts/append-progress.sh <progress-file> "review phase 1: findings"`
   Затем через pipe: `echo "<находки>" | bash SKILL_DIR/scripts/append-progress.sh <progress-file>`

3. **Если ВСЕ агенты сообщили о нулевых проблемах** → сообщи "Фаза ревью 1: чисто" и переходи к следующей фазе.

4. **Запусти агент-фиксер** — прочитай промпт фиксера из `SKILL_DIR/references/prompts/fixer.md`. Запусти с `subagent_type: "general"`. Передай ПОЛНЫЙ неизменённый вывод ревью как FINDINGS_LIST — фиксер сам решает, что реально, а не ты.

5. **После возврата фикстера** → покажи секцию "FIXES:" пользователю. Сообщи "Фаза ревью 1: итерация N — исправления применены". Вернись к шагу 1.

Если достигнут максимум итераций, а проблемы всё ещё найдены, сообщи "Фаза ревью 1: достигнут максимум итераций, продолжаем" и двигайся дальше.

### Шаг 8. Фаза ревью 2 — код-смеллы

Сообщи пользователю: "--- Фаза ревью 2: анализ код-смеллов ---"

Запусти один раз (без цикла):

1. **Запусти агент смеллов** — прочитай `SKILL_DIR/references/agents/smells.txt`. Добавь в начало то же ограничение только чтения, что и для агентов ревью (без git stash, checkout или reset). Запусти один вызов Task tool с `subagent_type: "general"` и промптом агента.

2. **Собери находки** — после возврата агента сообщи пользователю компактный список находок (одна строка на находку). Запиши находки в файл прогресса.

3. **Если проблем не найдено** → сообщи "Анализ смеллов: чисто" и переходи к следующей фазе.

4. **Запусти агент-фиксер** — прочитай промпт фикстера из `SKILL_DIR/references/prompts/fixer.md`. Запусти с `subagent_type: "general"`. Передай ПОЛНЫЙ вывод смеллов как FINDINGS_LIST.

5. **После возврата фикстера** → сообщи исправления пользователю. Переходи к следующей фазе.

### Шаг 9. Фаза ревью 3 — только критичное

2. **Собери находки** — передай ПОЛНЫЙ вывод агента ревью (не резюме) в fixer. НЕ резюмируй, не фильтруй и не отбрасывай ни одну находку. ВСЕ находки требуют действий. Сообщи пользователю краткий список находок. Запиши в файл прогресса:

### Шаг 10. Фаза ревью 4 — ручное ревью

Спроси пользователя через инструмент `question`:

```
header: "Ручное ревью"
question: "Запустить plannotator review для ручного ревью всех изменений?"
options:
  - label: "Да, запустить plannotator review"
    description: "Открыть UI Plannotator review для ручного ревью"
  - label: "Нет, пропустить"
    description: "Пропустить ручное ревью, перейти к завершению"
```

Если пользователь выбрал "Нет, пропустить" → сообщи "Фаза ревью 4: пропущена" и переходи к следующему шагу.

Если пользователь выбрал "Да", цикл до 10 раз. Отслеживай номер текущей итерации:

1. **Запусти plannotator** — выполни `bash SKILL_DIR/scripts/plannotator-review.sh` через bash. Это **блокирующий вызов** — он запускает сервер Plannotator review, открывает браузер и ждёт, пока пользователь нажмёт "Send Feedback" или "Approve". Вывод команды содержит обратную связь пользователя в виде структурированного текста. Bash tool заблокируется до завершения ревью пользователем.

2. **Разбери обратную связь** — вывод скрипта содержит решение ревью. Если вывод указывает на одобрение без обратной связи (например, `"approved": true` и пустой feedback) → сообщи "Фаза ревью 4: чисто" и переходи к следующему шагу. Иначе извлеки текст обратной связи.

3. **Собери находки** — сообщи обратную связь как краткий список пользователю. Запиши в файл прогресса:
   `bash SKILL_DIR/scripts/append-progress.sh <progress-file> "review phase 4: findings"`
   Затем через pipe: `echo "<находки>" | bash SKILL_DIR/scripts/append-progress.sh <progress-file>`

4. **Запусти агент-фиксер** — прочитай промпт фикстера из `SKILL_DIR/references/prompts/fixer.md`. Запусти с `subagent_type: "general"`. Передай ПОЛНЫЙ вывод обратной связи как FINDINGS_LIST — фиксер сам решает, что реально, а не ты.

5. **После возврата фикстера** → покажи секцию "FIXES:" пользователю. Сообщи "Фаза ревью 4: итерация N — исправления применены". Вернись к шагу 1.

Если достигнут максимум итераций, а проблемы всё ещё найдены, сообщи "Фаза ревью 4: достигнут максимум итераций, продолжаем" и двигайся дальше.

### Шаг 11. Завершение

Когда все ревью завершены:
- Запиши завершение в файл прогресса: `bash SKILL_DIR/scripts/append-progress.sh <progress-file> "completed"`
- Сообщи резюме: "Все N задач завершены, ревью пройдены"
- Если использовался worktree, сообщи: "Worktree по пути <path>, ветка: <branch-name>. Ревью и мерж на усмотрение."
- НЕ перемещай файл плана и не пушь — только сообщи о завершении

## Ключевые правила

- Каждый субагент получает чистый контекст — без накопленного состояния от предыдущих задач
- Родительская сессия отслеживает только: номер задачи, успех/провал, количество повторных попыток
- Файл плана — единственный источник истины для прогресса — всегда перечитывай его
- Никаких сигналов — только чекбоксы в плане для отслеживания прогресса задач
- Веди файл прогресса (`docs/progress/progress-<plan-name>.txt`)
- Не модифицируй файл плана сам — только субагенты модифицируют его
- Не реализуй и не исправляй код сам — только субагенты реализуют и исправляют
- Если субагент провалился или оставил сломанный код — перезапусти цикл — НЕ исследуй и не исправляй сам
- НИКОГДА не отбрасывай находки как "уже существовало", "не из изменений" или "архитектурные" — ВСЕ находки требуют действий
- НИКОГДА не резюмируй и не фильтруй находки агентов — передавай полный вывод агенту-фикстеру как есть
- Все файлы промптов и агентов читаются напрямую из директории скилла (без цепочки переопределения)
- Все значения `subagent_type` должны быть `"general"` — файлы агентов предоставляют специализированный промпт
- После чтения файла промпта подставь все плейсхолдеры перед передачей субагенту
