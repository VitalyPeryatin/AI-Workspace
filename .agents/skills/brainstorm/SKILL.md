# Brainstorm

Превращение идей в проектные решения через совместный диалог перед реализацией.

## Процесс

### Этап 1: Понимание идеи

Сначала изучи контекст проекта, затем задавай вопросы по одному:

1. **Собери контекст** — изучи файлы, документацию, последние коммиты, относящиеся к идее
2. **Задавай вопросы по одному** — предпочитай варианты с выбором ответа
3. **Сосредоточься на**: назначении, ограничениях, критериях успеха, точках интеграции

Не перегружай несколькими вопросами. Один вопрос на сообщение. Если тема требует углубления — разбей на несколько вопросов.

### Этап 2: Исследование подходов

Когда проблема понята:

1. **Предложи 2-3 разных подхода** с оценкой компромиссов
2. **Начни с рекомендуемого варианта** и обоснуй выбор
3. **Представляй в формате диалога** — пока не формальный документ

Пример формата:
```
Вижу три подхода:

**Вариант А: [название]** (рекомендуемый)
- как работает: ...
- плюсы: ...
- минусы: ...

**Вариант Б: [название]**
- как работает: ...
- плюсы: ...
- минусы: ...

Какое направление тебе ближе?
```

### Этап 3: Представление дизайна

После выбора подхода:

1. **Разбей дизайн на секции** по 200-300 слов каждая
2. **Спрашивай после каждой секции** — всё ли выглядит правильно
3. **Покрой**: архитектуру, компоненты, поток данных, обработку ошибок, тестирование
4. **Будь готов вернуться назад** — если что-то не складывается

Не представляй весь дизайн сразу. Пошаговая валидация выявляет недопонимания на ранних этапах.

### Этап 4: Следующие шаги

После валидации дизайна спроси пользователя, что делать дальше:

- **Написать план**: вызови скилл `writing-plans` через skill tool для создания детального плана реализации. Передай контекст brainstorm (найденные файлы, выбранный подход, проектные решения), чтобы план имел полный контекст без повторных вопросов
- **Написать дизайн-документ**: сохрани валидированный дизайн в `docs/design/YYYY-MM-DD-<task-name>.md` (имя `<task-name>` — от темы brainstorm, в kebab-case). Создай директорию `docs/design/`, если её нет. Включи все секции из Этапа 3 (архитектура, компоненты, поток данных, обработка ошибок, тестирование) вместе с выбранным подходом и ключевыми решениями
- **Начать сейчас**: приступить к реализации напрямую, если дизайн достаточно прост

## Ключевые принципы

- **Один вопрос за раз** — не перегружай несколькими вопросами
- **Выбор из вариантов** — проще отвечать, чем формулировать открытый ответ, когда возможно
- **YAGNI безжалостно** — убирай ненужные фичи из всех дизайнов, минимизируй объём
- **Исследуй альтернативы** — всегда предлагай 2-3 подхода перед тем как остановиться на одном
- **Пошаговая валидация** — представляй дизайн секциями, валидируй каждую
- **Будь гибким** — возвращайся и уточняй, если что-то непонятно
- **Начинай с рекомендации** — имей мнение, объясняй почему, но решение за пользователем
- **Дублирование vs абстракция** — когда код повторяется, спроси пользователя: предпочитаешь дублирование (проще, нет связанности) или абстракцию (DRY, но добавляет сложность)? объясни компромиссы перед решением

## Отслеживание задач

При реализации после brainstorm:
- Отслеживай задачи реализации с помощью доступных инструментов управления задачами (списки задач, чекбоксы в файле плана или аналогичные)
- Отмечай каждую задачу выполненной сразу после завершения (не накапливай)
- Информируй пользователя о прогрессе через обновления статуса
