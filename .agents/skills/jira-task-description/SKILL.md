# Jira Task Description

Пишешь короткое, структурированное описание задачи на русском языке в формате Jira wiki markup.

## Формат

Только Jira wiki markup, не Markdown:

- Заголовки: `h2.`, `h3.` и т.д. — заголовок и текст разделены пустой строкой
- Нумерованный список: `# пункт`
- Маркированный список: `* пункт`, вложенность — `** пункт`
- Жирный текст: `*текст*`
- Ссылки: просто URL (Jira сам их отрендерит)

## Структура

Обязательные разделы — всегда, в этом порядке:

```
h3. Цель
h3. Бизнес-ценность
h3. Оценка объёма работ
h3. Критерии приёмки
```

Дополнительные разделы (по мере необходимости, между «Оценкой» и «Критериями» или после них):
*Описание процесса*, *Роли и ответственность*, *Технические детали*, *Ссылки*, *Риски* —
подбери под конкретную задачу. Не добавляй разделы ради объёма.

По умолчанию оценка объёма — в днях (например, «4 дня»). Если задача явно
не влезает в дни (например, «2 часа» на мелкий фикс) — используй подходящие единицы.

## Лимиты символов

Считай символы по итоговому тексту **вместе с разметкой** (h3., *, # и т.д.):

1. Цель — **не более 800 символов**.
2. Превышение до 1500 допустимо **только** для особо сложных, многоуровневых задач.
3. **1500 символов — жёсткий предел, превышать запрещено.**

Причины: описание читают за секунды перед взятием задачи в работу и на рефайне.
Короткое описание заставляет сначала думать, потом писать — и его реально читают.

## Процесс

### Шаг 1. Уточни вводные

Перед написанием проверь, что понимаешь: **что** нужно сделать, **зачем** (бизнес-контекст),
**как поймём, что готово** (критерии приёмки), **сколько это займёт**.

Если чего-то не хватает или что-то непонятно — задай пользователю вопросы и дождись ответа.
Не выдумывай цель, цифры оценки и критерии приёмки: это именно то, что нельзя фантазировать.
Вопросы задавай списком, одним сообщением — не по одному.

Если пользователь просит «просто напиши» и всё очевидно из контекста — пиши без вопросов,
но явно пометь допущения (например, оценку) как предположение.

### Шаг 2. Напиши черновик

- Пиши списками, а не простынями текста — они короче и читаются быстрее.
- Каждый критерий приёмки — отдельный пункт нумерованного списка, проверяемый фактами
  («Раскатка проходит раз в 2 недели»), а не пожелание («раскатка должна быть регулярной»).
- Не дублируй одно и то же в «Цели» и «Критериях приёмки»: цель — зачем, критерии — как проверим.

### Шаг 3. Посчитай символы и ужми при необходимости

Посчитай символы черновика с разметкой. Для точности удобно использовать bash:

```bash
printf '%s' "<текст черновика>" | wc -m
```

Если больше 800 — сначала сокращай без потери смысла:

- убери дополнительные разделы;
- слей похожие пункты;
- режь вводные слова и канцелярит;
- оставь только те ссылки, без которых задачу не выполнить.

Больше 800 — только если задача действительно сложная и многоуровневая.
Больше 1500 — никогда: продолжай резать.

### Шаг 4. Выдай результат

Весь текст описания — **в одном блоке кода**, чтобы пользователь мог скопировать одной
кнопкой. Вне блока укажи итоговое количество символов. Примеры и пояснения вне блока
не добавляй, если не просят.

## Пример

Эталон стиля и уровня детализации. Это процессная задача, поэтому добавлены дополнительные разделы:

```
h3. Цель

Регулярная, предсказуемая доставка FMS в BDUI без дефектов на проде

h3. Бизнес-ценность

Поддержка новых возможностей в продуктовых фичах для всего АльфаБанка

h3. Оценка объёма работ

4 тех дня

h3. Описание процесса

# *Ритм:* раз в 2 недели. Конкретные даты — по графику релизов FMS 2026
# *Процесс раскатки:* строго по регламенту «Адаптации FMS для Дежурных FMS»
# *Целевая среда:* BDUI-админка — https://bdui-management-ui.admin-int.moscow.alfaintra.net

h3. Роли и ответственность

* *Регресс-капитан* — владелец процесса раскатки и регресса:
** следит за соблюдением сроков раскатки по графику;
** отвечает за прогон обязательной валидации BDUI-контрактов и принятие решения «выкатывать/не выкатывать» по её результатам;
** гарантирует отсутствие багов на проде после раскатки (через регресс по регламенту и контроль после выкатки).
* *Дефекты прода после раскатки:* любой дефект прода, найденный после раскатки FMS, по умолчанию заводится *на команду регресс-капитана*.

h3. Критерии приёмки

# Раскатка FMS проходит регулярно - 1 раз каждые 2 недели
# Отсутствуют дефекты прода после раскаток FMS
```

Для простой задачи хватит только четырёх обязательных разделов.
