# Отчёт: вложенные оркестраторы в OpenCode

**Дата:** 23.08.2026
**Окружение:** OpenCode 1.18.18, модель deepseek-v4-flash (ollama-cloud), macOS
**Проект:** `/Users/vitalyperyatin/AI_Workspace`

## 1. Как проводился эксперимент

### 1.1 Цель

Практически измерить, насколько возрастает расход токенов при увеличении глубины оркестрации
(«оркестратор внутри оркестратора») в реальной конфигурации OpenCode пользователя
(большой системный контекст: инструкции, MCP-серверы, permissions).

### 1.2 Сетап

Создана серия агентов в `.opencode/agents/`:

| Агент | Mode | Роль | Делегирование |
|---|---|---|---|
| `nest-direct` | primary | baseline, решает сам | `task: deny` |
| `nest-orch-1` | all | оркестратор уровня 1 | только `nest-worker` |
| `nest-orch-2` | all | оркестратор уровня 2 | только `nest-orch-1` |
| `nest-orch-3` | all | оркестратор уровня 3 | только `nest-orch-2` |
| `nest-worker` | subagent | лист дерева, исполнитель | `task: deny` |

Задачи: 4 идентичных по сложности (реализовать `fizzbuzz(n)` + doctest, проверка `python3 -m doctest`),
каждая — своя глубина оркестрации. Прогон через `opencode run --agent nest-* --title nest-exp-depth-N --auto`.

Учёт: SQLite-база `~/.local/share/opencode/opencode.db` — сессии с `parent_id`
(дерево «родитель → субагент»), агрегированные `tokens_input/output/reasoning/cache_read`, `cost`.
Валидатор `nest-exp/validate_tokens.py` строит дерево по `parent_id` и считает токены по уровням.

**Прогонов:** 4 (1 пилотный + 3 для усреднения; у каждой глубины — 3 полных замера).
Артефакты: `nest-exp/run_experiment.sh`, `nest-exp/validate_tokens.py`, `nest-exp/logs/`, `nest-exp/tasks/`.

### 1.3 Хронология и ключевые открытия

1. **Пилотный прогон** — глубины 2 и 3 «схлопнулись»: оркестраторы получали
   `Subagent depth limit reached (1)`. Вложенность глубже 1 уровня **заблокирована по умолчанию**.
2. В конфиг проекта добавлено `"subagent_depth": 3` — полная цепочка заработала
   (`nest-orch-3 → nest-orch-2 → nest-orch-1 → nest-worker`).
3. Обнаружено: `opencode run --agent` не принимает агентов с `mode: subagent` (фолбэк на default) —
   оркестраторам, которые должны быть и корнем, и субагентом, нужен `mode: all`.
4. Три полных прогона для усреднения (старты логируются в `logs/experiment_starts.txt`).

## 2. Результаты

### 2.1 Суммарные токены по глубинам (3 замера, модель deepseek-v4-flash)

| Глубина | Прогон 1 | Прогон 2 | Прогон 3 | Среднее | Медиана | σ |
|---|---:|---:|---:|---:|---:|---:|
| 0 (baseline, напрямую) | 158.1k | 158.4k | 158.0k | **158.1k** | 158.1k | 0.2k |
| 1 (orch → worker) | 318.3k | 318.4k | 320.1k | **318.9k** | 318.4k | 1.0k |
| 2 (orch → orch → worker) | 427.2k | 1036.4k* | 427.7k | 630.5k | **427.7k** | 351.6k |
| 3 (orch → orch → orch → worker) | 650.3k | 976.1k | 980.9k | 869.1k | **976.1k** | 189.5k |

\* выброс: оркестратор уровня 2 сам верифицировал результат (ls/find/Read, 3× запуск doctest).

### 2.2 Оверхед относительно baseline

Медианы из таблицы 2.1, baseline = медиана глубины 0 (158.1k).

| Глубина | Δ токенов | Δ % | Доля координации (не-исполнитель) |
|---|---|---:|---:|---:|
| 0 | — | — | — |
| 1 | +160.3k | **+101%** | 34% |
| 2 | +269.6k | **+171%** | 46% |
| 3 | +818.0k | **+517%** | 56% |

Пример расчёта Δ % для глубины 1: (318.4 − 158.1) / 158.1 = 1.014 → **+101%**.

### 2.3 Как считались метрики

**Оверхед (Δ %)** — медиана глубины относительно медианы baseline:

```
Δ % = (медиана_глубины − медиана_baseline) / медиана_baseline × 100%
```

**Доля координации** — структурный расчёт по дереву сессий (строится через `parent_id`):
лист дерева (самый глубокий уровень = исполнитель) считается «полезной работой»,
всё остальное (корень + промежуточные оркестраторы, целиком, включая их системный контекст) — «координацией»:

```
координация = Σ(все токены дерева) − Σ(токены листа)
доля координации = координация / Σ(все токены дерева) × 100%
```

Усреднение по прогонам — отношение средних: `mean(координация_i) / mean(суммарно_i) × 100%`.

Пример (глубина 3, прогон 1): дерево = 162.4k + 109.0k + 110.1k + 268.8k = 650.3k;
лист (nest-worker) = 268.8k; координация = 650.3 − 268.8 = 381.5k → 58.7%.

**Множитель расходов** (раздел 3.3) — то же, что Δ %, но в разах:

```
множитель = медиана_глубины / медиана_baseline
```

### 2.4 Типичная структура расходов на один уровень (из замеров)

| Сессия | Input (типично) | Комментарий |
|---|---:|---|
| Пустой оркестратор (L0-слой) | ~106–107k | Полная загрузка системного контекста (instructions, MCP, permissions) |
| Следующий оркестратор | ~107k | То же |
| Исполнитель (реальная работа) | ~211k | Работа + пересказ задачи вниз + саммари вверх |
| Оркестратор-верификатор (паттерн из выбросов) | +300–600k | Перечитывание файлов, повторные проверки |

### 2.5 Выводы

1. **Минимальная цена уровня ≈ полный системный контекст (~106k input у нас)**, т.к. каждая
   сессия загружает его заново. Это +66–70% к суммарному расходу за каждый добавленный уровень
   даже при идеально дисциплинированных агентах.
2. **Реальная цена выше: +100% (L1), +171% (L2), +517% (L3)** — модель статистически склонна
   к самостоятельной верификации («не доверяю саммари, прочитаю сам»), что раздувает расходы
   в 2–2.5 раза на глубоких уровнях.
3. **Глубины 0–1 стабильны (σ ≈ 0.2–1k), глубже — разброс огромен** (σ до 350k).
4. Стоимость `cost` в БД у ollama-cloud = 0; на платных моделях добавится денежная метрика
   (пропорциональна токенам).

## 3. Что необходимо для работы вложенных оркестраторов в OpenCode

### 3.1 Конфигурация (обязательно)

```jsonc
// opencode.json (проектный конфиг)
{
  "subagent_depth": 2,        // 1. БЕЗ ЭТОГО вложенность глубже 1 НЕ РАБОТАЕТ:
                              //    субагенты не могут запускать субагентов
                              //    ("Subagent depth limit reached (1)").
                              //    Значение = максимальная глубина цепочки.
                              //    Для текущей схемы (android-orch → executor) достаточно 1,
                              //    для будущей (PO → android-orch → executor) — 2.
  "agent": {
    "android-orch": { "mode": "all" }   // 2. mode: all — чтобы агент был и корнем
                                        //    (opencode run --agent), и субагентом (task tool)
  }
}
```

### 3.2 Правила для каждого агента-оркестратора

- **`mode: all`** — `mode: subagent` нельзя запустить как корень через `--agent` (фолбэк на default).
- **`permission.task`** — жёсткий allowlist того, кому можно делегировать:
  ```jsonc
  "permission": {
    "task": { "*": "deny", "android-executor": "allow", "android-reviewer": "allow" }
  }
  ```
  При `deny` субагент удаляется из описания task tool — модель даже не попытается его вызвать.
- **`hidden: true`** — убрать внутренние агенты из @-меню (работает для `mode: subagent`;
  оркестраторы с `mode: all` остаются видимыми — это удобно для прямого вызова разработчиком).
- **Модель** — субагент наследует модель вызывающего; на глубоких цепочках лучше задавать
  `model:` явно каждому уровню.
- **Запрет верификации на верхних уровнях** — главный рычаг экономии:
  `permission: { "read": "deny" }` у оркестраторов (кроме доступа к task). По замерам это
  экономит 50–60% расходов глубоких цепочек.

### 3.3 Чего это стоит (измерено в нашем окружении)

| Глубина цепочки | Множитель расходов |
|---|---|
| 0 (агент сам) | 1.0× |
| 1 (агент → исполнитель) | ~2.0× |
| 2 (агент → орк → исполнитель) | ~2.7× |
| 3 (агент → орк → орк → исполнитель) | ~6.2× (медиана) |

**Откуда взялись цифры.** Множитель — это медиана суммарных токенов глубины (таблица 2.1),
делённая на медиану baseline:

| Глубина | Медиана | Множитель (медиана / 158.1k) |
|---|---:|---:|
| 0 | 158.1k | 1.0× (база) |
| 1 | 318.4k | 318.4 / 158.1 = **2.0×** |
| 2 | 427.7k | 427.7 / 158.1 = **2.7×** |
| 3 | 976.1k | 976.1 / 158.1 = **6.2×** |

Пример чтения: цепочка «агент → орк → исполнитель» стоит в ~2.7 раза дороже, чем
тот же агент, решивший задачу сам.

На реальных задачах (где работа исполнителя ≫ fizzbuzz) абсолютный оверхед «размывается»,
но относительные множители сохраняются.

## 4. Целевая схема работы: PO и ИИ-инженер

### 4.1 Решение

- **Существующий PO-оркестратор не трогаем** — он остаётся как есть и работает
  только со своими текущими задачами.
- **Создаём `android-orch`** (mode: all) — платформенный оркестратор для Android.
  У него два клиента:
  - **ИИ-инженер** — вызывает `@android-orch` напрямую (основной путь);
  - **PO-оркестратор** — сможет вызывать его **в будущем**, когда/если PO-уровень
    начнёт маршрутизировать платформенные задачи.
- При этом **сам `android-orch` не знает про PO-оркестратора**: он принимает
  задачу (текст или путь к файлу спеки) от любого вызывающего и работает
  с ней одинаково.

### 4.2 Архитектура

```
                ┌──────────────────────────────────────────┐
                │  ИИ-инженер (основной путь, сейчас)      │
                └───────────────┬──────────────────────────┘
                                │ @android-orch (напрямую,
                                │  без PO-уровня)
                                ▼
                ┌──────────────────────────────────────────┐
                │  PO-оркестратор (существующий, НЕ трогаем)│
                │  executor / reviewer                      │
                └───────────────┬──────────────────────────┘
                                │ ── в будущем ──► @android-orch
                                ▼   (когда PO начнёт
                ┌──────────────────────────┐   маршрутизировать
                │  @android-orch (mode: all)│   платформенные задачи)
                │  → android-executor       │
                │  → android-reviewer       │
                └──────────────────────────┘
```

`android-orch` не знает, кто его вызвал: он принимает задачу (текст или путь
к файлу спеки) от любого клиента и работает с ней одинаково.

### 4.3 Конфигурация `android-orch`

```jsonc
// .opencode/agents/android-orch.md (frontmatter)
---
name: android-orch
description: Оркестратор Android-задач. Принимает задачу или путь к файлу спеки,
             делегирует android-executor и android-reviewer, возвращает итог.
mode: all          // можно запускать и как корень (opencode run --agent / @android-orch),
                   // и как субагента (из PO-оркестратора через task tool)
permission:
  task:
    "*": deny            // только перечисленные ниже субагенты
    "android-executor": "allow"
    "android-reviewer": "allow"
  read: deny             // НЕ верифицирует код сам (главный рычаг экономии,
                         // см. 2.5): доверяет саммари executor, проверяет reviewer
---
...системный промпт: разбор задачи, передача executor'у (путь к спеке, а не пересказ),
2 цикла правок максимум, саммари до 300 слов...
```

Требования к конфигу проекта:

```jsonc
// opencode.json — уже стоит 3 (добавлено в эксперименте, см. 1.3):
{ "subagent_depth": 3 }
// Минимум для текущей схемы — 1 (android-orch → executor),
// для будущей (PO → android-orch → executor) — 2. Стоящее значение 3
// покрывает обе схемы с запасом.
```

### 4.4 Принципы, вытекающие из эксперимента

1. **Платформенный (Android) оркестратор — точка входа для всех**, кто работает с Android:
   и инженер, и (в будущем) PO-уровень. Единый путь — проще поддерживать и контролировать.
2. **Спека передаётся как путь к файлу, а не пересказ** — пересказ = искажение смысла
   + двойной расход токенов (замерено: каждая передача вниз добавляет ~106k системного
   контекста новой сессии).
3. **Верхние уровни не верифицируют** (`read: deny` на код) — иначе срабатывает паттерн
   «оркестратор-верификатор» с раздуванием в 2–2.5 раза (зафиксировано в прогонах L2/L3).
   Проверку отдаёт `android-reviewer` — это его работа.
4. **`subagent_depth` в конфиге** — стоит 3 и покрывает любую будущую цепочку
   (ИИ-инженер → android-orch → executor); минимум для текущей схемы — 1.

### 4.5 План внедрения

1. Создать `android-orch` (mode: all) + `android-executor` / `android-reviewer` (mode: subagent)
   в `.opencode/agents/` по шаблону из 4.3.
2. `subagent_depth: 2` в `opencode.json`
3. Сделать шаблон спеки (`specs/` + пример): контекст, требования, критерии готовности,
   платформа — чтобы `android-orch` и инженер говорили на одном языке.
4. ИИ-инженеру — документ: «Android-задачи вызывай через `@android-orch` напрямую;
